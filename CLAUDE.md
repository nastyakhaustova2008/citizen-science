# CLAUDE.md — מִצְפֶּה (Field)

## О проекте

Школьная сеть гражданской науки. Ученики делают измерения по единому протоколу (температура, влажность, яркость неба, PM2.5) и отмечают их на общей карте. Mobile-first. Язык по умолчанию — иврит (RTL).

## Текущий статус

* Бэкенд — Supabase, таблицы `campaigns`, `campaign_fields`, `campaign_field_options`, `measurements`.
  * Кампании: `AppDataContext` читает их из базы (только чтение) вместе с полями формы и переводит строки в прежний формат Observation (`titleHe/En/Ru`, `center: [lat, lng]` и т. д.) + `fields`, `primaryField`, `formVersion`, `scale`. Искать кампанию — через `getObservation(idOrSlug)` из `useAppData()`, не из mockData. Состояния: `campaignsLoading`, `campaignsError`, `reloadCampaigns`; `refreshCampaigns()` — перечитать без состояния загрузки (открытые формы не теряют ввод).
  * `campaigns.metric` теперь необязателен: это только ключ пресета цветов в `metrics.js` (цвета, диапазон шкалы, «правдоподобный» диапазон, шаг гистограммы) и фильтр тем на главной. Единица, знаки и подпись значения берутся из основного поля. Неизвестный/пустой `metric` → цвета по умолчанию, кампания не пропускается.
  * Измерения: `AppDataContext` читает их из базы и сохраняет новые; состояния: `measurementsLoading`, `measurementsError`, `reloadMeasurements`. Значения — `m.values` (`field_values` в базе, ключи = ключи полей), `m.formVersion`. `m.value` — вычисляемое значение основного поля (null, если нет) для карты, графиков, статистики.
  * Форма измерения строится из полей кампании («движок форм», шаг 3) — см. раздел «Поля кампаний (движок форм)».
  * Страницы, где есть кампании (главная, кампания, добавление, протокол, профиль), показывают loading/error, пока кампании не загрузились.
* Аккаунты (шаг 4a) — Supabase Auth + таблица `profiles`, см. раздел «Аккаунты». `AuthContext` (`useAuth()`): сессия, профиль, `currentUser`, вход/регистрация/Google/сброс пароля. `useAppData().currentUser` — тот же пользователь.
* Роли (шаг 4b) — владелец / главные админы / админы, назначение и каскадное снятие, переименование, журнал; всё проверяется в базе (миграция 009). Панель «Администрирование» — в своём профиле у админов (вкладки Лабораторные · Пользователи · Журнал). См. раздел «Роли».
* Редактор лабораторных (шаг 5a, миграция 010) — профиль админа, черновики, редактор (описание, поля, протокол, предпросмотр), косметическая правка опубликованных, журнал лабораторных. См. раздел «Редактор лабораторных».
* Проверка и публикация (шаг 5b, миграция 011) — отправка на проверку, 3 одобрения, «запросить изменения», публикация, публичные «Создано / Одобрено». См. раздел «Проверка лабораторных».
* Ревизии опубликованных (шаг 5c, миграция 012) — изменения структуры и протокола опубликованной лабораторной как предлагаемая версия с 3 одобрениями; ученики до этого работают со старой формой. См. раздел «Ревизии опубликованных лабораторных».
* Политика конфиденциальности — статическая страница `public/privacy.html` (he/en/ru), см. раздел «Политика конфиденциальности».
* Всё остальное пока захардкожено в `src/data/mockData.js`: демо-пользователи (авторы демо-измерений), форум (темы/посты/реакции), бейджи, «присоединиться к кампании».
* `OBSERVATIONS` в mockData остался **только** для генерации оставшихся моков; UI его не импортирует. Кампании менять в базе, не там.
* Ещё на моках (читают `MEASUREMENTS` из mockData, а не из базы): лента активности и счётчик школ на главной, `participantsCount`, график вклада в профиле. Счётчик активных кампаний на главной считается из базы.
* Только в памяти, теряется при перезагрузке: комментарии к точкам, пометки «проблема» (flag), фото, загруженные учениками (`m.photos[ключ поля]`; в базе у поля-фото хранится только `true` — «фото приложено»; Storage — позже), новые темы/посты форума. Писать их (и реакции) можно только после входа; без входа — `LoginPrompt`.
* Доступ (RLS):
  * `measurements`: все читают. Добавлять — только вошедший пользователь и только от своего имени (`user_id = auth.uid()`, у профиля есть имя), статус `pending`. Изменять/удалять нельзя. Каждое добавление проверяется триггером по текущим определениям полей. До запуска 007 ещё действует TEMPORARY-правило «все добавляют» (для старого кода production).
  * `profiles`: все читают `id, username, role, created_at`; писать напрямую никто не может (только триггер, RPC и SQL Editor). `role_granted_by/at` — только через `admin_list_users` (админам).
  * `campaigns`, `campaign_fields`, `campaign_field_options`: опубликованные (`publication = 'published'`) читают все, черновики и «на проверке» — только админы (поля/варианты видны, если видна кампания). **Прямой записи нет ни у кого** — только RPC `lab_save` / `lab_delete` (010). Редактировать: автор (`created_by`), главные админы, владелец. Удалять: главный админ и владелец любую, обычный админ — только свою; и только без измерений. У `campaigns` чтение по списку колонок (`created_by` не публичен): **новой колонке нужен свой `grant select (колонка)`**.
  * `admin_profiles`: свою строку читает сам, все строки — админы; пишет только `admin_profile_save`. Публично — только через функцию авторов/одобривших на лабораторной (5b).
  * `lab_events` (журнал лабораторных): читают админы через `lab_log`, пишут только функции 010/011.
  * `lab_reviews` (одобрения и запросы изменений; `revision_id` — у проверок ревизий): прямого доступа нет; админы читают через `lab_review_history`, публично — только имена/места работы/дата одобривших через `lab_credits`.
  * `lab_revisions` (предлагаемые версии опубликованных): прямого доступа нет, только функции 012 (`lab_revision_get` — админам).
  * `role_events` (журнал ролей и переименований): читают только админы, пишут только функции 009.
* Внешний ключ `measurements.observation_id → campaigns.id` (`on delete restrict`): нельзя добавить измерение к несуществующей кампании и удалить кампанию, у которой есть измерения. Измерение можно добавить только в опубликованную лабораторную (триггер, `lab_not_published`).
* `src/hooks/useMockLoad.js` (имитация загрузки, setTimeout ~550 мс) сейчас нигде не используется — оставлен для будущих мок-экранов.
* Деплой: GitHub → Vercel. (В репо также лежит `netlify.toml` — остаток, не используется.)

## Стек

* Vite 5 + React 18, JavaScript (JSX), без TypeScript
* Бэкенд: Supabase (@supabase/supabase-js) — таблицы `campaigns`, `campaign_fields`, `campaign_field_options`, `measurements`, `profiles`; Supabase Auth (PKCE); Edge Function `account` (Deno, обычный JS)
* react-router-dom 6 (HashRouter)
* Tailwind CSS 3
* Карта: leaflet + react-leaflet + react-leaflet-cluster, тайлы OpenStreetMap
* Графики: recharts
* Иконки: lucide-react
* Линтеров и тестов нет

## Команды

* `npm install` — зависимости (Node 18+)
* `npm run dev` — dev-сервер, http://localhost:5173
* `npm run build` — сборка в `dist/`
* `npm run preview` — просмотр сборки

## Переменные окружения

* `VITE_SUPABASE_URL` — URL проекта Supabase
* `VITE_SUPABASE_ANON_KEY` — publishable (anon) ключ Supabase
* В Vercel заданы для всех окружений. Локально — файл `.env.local` в корне (в `.gitignore`, не коммитить). После изменения перезапустить `npm run dev`.
* Если переменных нет, `supabase` = `null` и измерения показывают состояние ошибки.
* Edge Function `account` берёт ключи из стандартных секретов Supabase (`SUPABASE_URL`, `SUPABASE_SECRET_KEYS`); свои секреты (лимиты, `CLIENT_IP_HEADER`) — в Dashboard → Edge Functions → Secrets, см. `supabase/SETUP_AUTH.md`.
* Имена не менять. Серверные ключи (service_role/secret) во фронтенд не класть.

SQL запускается вручную в Supabase SQL Editor, по номерам: 001 migration → 001 seed → 002 migration → 002 seed → 003 migration → 004 migration → (003 seed) → 005 migration → 006 migration → (после деплоя production) 007 migration. 008 — в любой момент после 006 (с 007 не связана). 009 — после 006 и назначения владельца (совместима со старым кодом, с 007/008 не связана; `SETUP_AUTH.md` → 13). 010 — после 009, затем seed 004; ломает только назначение админа из старого кода (новый обязательный аргумент), поэтому: 010 → preview → merge → деплой production. 011 — после 010, совместима с кодом 5a (`SETUP_AUTH.md` → 15). 012 — после 011, совместима с кодом 5b (`SETUP_AUTH.md` → 16). Seed 001 пишет в колонку `value` и работает только до 005. Seed-файлы только вставляют данные, схему не меняют. Supabase CLI не используется. Новые изменения схемы — новым файлом `00N_*.sql`, старые миграции не редактировать.

Порядок выкладки миграций, несовместимых со старым кодом (как 004/005, 006/007): миграция → проверка на preview (Vercel) → merge → дождаться деплоя production → миграция, ломающая старый код (005, 007). Между 004 и деплоем нового кода production **не может добавлять измерения**. 006 совместима со старым кодом; 007 — нет (старый код добавляет как anon).

## Поля кампаний (движок форм)

* Место (`lat`, `lng`, `place_label`), дата/время (`measured_at`), автор, статус — встроенные колонки `measurements`, не поля.
* Всё остальное — поля: `campaign_fields` (PK `campaign_id, key`) и варианты `campaign_field_options` (PK `campaign_id, field_key, key`). Подписи и подсказки — `label_he/en/ru`, `help_he/en/ru`.
* Типы: `number` (`unit`, `min_value`, `max_value`, `decimals` — обязательно), `choice`, `multi_choice` (варианты), `text` (`text_long`: короткий ≤200 / длинный ≤2000), `boolean`, `datetime` (ISO-строка), `photo` (пока `true`).
* Основное поле (`is_primary`): одно числовое неархивное поле на кампанию — цвета карты, легенда, графики, статистика. Нет основного поля → кампания работает, но без цветов и графиков.
* Значения измерения — `measurements.field_values` (jsonb `{ключ поля: значение}`), выбор хранится ключом варианта, мультивыбор — массивом ключей. Пустые значения не хранятся.
* Правила изменений (проверяются триггерами в базе, не обходить):
  * Ключи полей и вариантов никогда не меняются. Тип и единица поля тоже — нужно другое → новое поле.
  * Подписи, подсказки, порядок, обязательность, min/max/decimals, основное поле — можно менять.
  * Поле/вариант не удаляют, а архивируют (`archived = true`): в форме не показывается, старые данные видны в панели точки, таблице и экспорте (с пометкой). Удаление разрешено, только пока у кампании нет ни одного измерения.
  * Варианты можно добавлять и архивировать, удалять нельзя.
  * Любое изменение полей/вариантов увеличивает `campaigns.form_version` (один раз за транзакцию); уменьшить нельзя. Новая кампания, созданная вместе с полями в одной транзакции, начинает с версии 1.
  * Ключи: `^[a-z][a-z0-9_]{0,39}$`, не оканчиваются на `_unit`, не совпадают со встроенными колонками экспорта (`id`, `date`, `lat`, `place`, …).
* Проверка при добавлении (триггер `measurements_validate_values`): значения сверяются с **текущими** определениями (неизвестные/архивные ключи, обязательность, тип, min/max, знаки, длина, варианты). Если всё верно — измерение сохраняется с текущим `form_version` (даже если форма была открыта на старой версии). Если нет — ошибка `invalid_values`, в `details` JSON `{ключ: код}`. Мастер тогда перечитывает кампанию (`refreshCampaigns`), сохраняет ввод ученика и подсвечивает поля.
* Экспорт: колонки полей называются ключами полей, у чисел есть `<ключ>_unit`, выбор — ключи вариантов, мультивыбор через `;`.

## Аккаунты (шаг 4a)

* Вход по **имени пользователя** + паролю, email необязателен; или через Google. Ручные настройки — `supabase/SETUP_AUTH.md`.
* Supabase Auth входит по email, поэтому регистрация, вход по имени и «забыли пароль» идут через Edge Function `account` (секретный ключ): имя → email ищется только на сервере (`account_lookup`), браузер никогда не получает чужой email и не может узнать, есть ли он у пользователя. Ответ «забыли пароль» всегда одинаковый, письмо отправляется в фоне.
* Без email у аккаунта внутренний адрес `<uuid>@noemail.mitzpe.invalid` (подтверждён, писем не получает). `isPlaceholderEmail()` — никогда его не показывать. Настоящий email (при регистрации или в профиле) добавляется через `updateUser({ email })` → письмо с подтверждением; до подтверждения он не используется. Поэтому «Secure email change» в Supabase выключен.
* Письма (сброс, смена email) — шаблоны с `token_hash`: `{{ .RedirectTo }}#/auth/confirm?token_hash=…&type=recovery|email_change|email` → `ConfirmPage` вызывает `verifyOtp` по кнопке. Google — PKCE: возвращается на `…/?code=…#/путь`, `AuthContext` убирает `?code` из адреса.
* `profiles`: `id` (= auth user id), `username` (null, пока пользователь Google не выбрал; выбирается один раз — `set_my_username`), `username_key` (без учёта регистра, уникален), `role` (`student` | `admin` | `main_admin` | `owner`), `role_granted_by`, `role_granted_at`, `created_at`. Профиль создаёт триггер на `auth.users` (имя — из `user_metadata.mitzpe_username`, его ставит только функция). Пользователь не может менять свою роль: у `anon`/`authenticated` нет прав на запись, триггер `profiles_guard` запрещает менять поля ролей из API, `owner` — только из SQL Editor и только один.
* Имя: после NFC, trim и схлопывания пробелов 3–24 символа — буквы иврита/латиницы/кириллицы, цифры, пробел, точка; начинается с буквы/цифры; точка только после буквы/цифры; хотя бы одна буква; латиницу и кириллицу не смешивать; не из списка зарезервированных. Пароль — 8–72 байта.
* Лимиты в функции (`private.rate_limit_hits`, IP хранятся только как HMAC): регистрации на IP и общий лимит в час, неудачные входы на имя, сбросы на IP и на имя. IP клиента берётся из заголовка платформы (не из левой части `X-Forwarded-For`) и передаётся в Supabase Auth как `Sb-Forwarded-For`; проверка на подделку — `SETUP_AUTH.md` → 8a.
* Авторы: `getAuthor(userId)` из `useAppData()` → реальный профиль (UUID, подгружается `loadAuthors`), демо-пользователь из mockData для старых измерений (`u-noa` …, `kind: 'demo'`, показывается с меткой «демо») или `null` («неизвестный участник»). Школу у реальных пользователей не собираем (фильтр/график «моя школа» у них скрыт).

## Роли (шаг 4b)

* Роли в `profiles.role`: `owner` (один, **только из SQL Editor**), `main_admin`, `admin`, `student`. `role_granted_by` — кто назначил (цепочка для каскада), `role_granted_at` — когда.
* Кто что может (функции `security definer` в 009, каждая сама проверяет роль вызывающего; одна advisory-блокировка на все изменения ролей):
  * `admin_grant_admin` — любой админ: ученика с именем → админ (`granted_by` = он).
  * `admin_revoke_admin` — владелец и главные админы: любого обычного админа; обычный админ — только тех, кого назначил сам. Каскад: он и все ниже по цепочке → ученики, `granted_by` очищается (повторное назначение цепочку не возвращает).
  * `owner_make_main_admin` — только владелец: ученика или админа → главный админ (его цепочка остаётся под ним).
  * `owner_demote_main_admin(target, 'admin'|'student')` — только владелец: «обычный админ» (цепочка остаётся) или «ученик» (каскад).
  * `admin_rename_user` — владелец: кого угодно, себя тоже (только имя; роль владельца — только SQL); главный админ: учеников и админов; админ: учеников. Правила имён те же (`username_error`).
  * Себя снять нельзя никому.
* Перед каскадом UI вызывает `admin_revoke_preview` и передаёт показанные id; если цепочка изменилась — ошибка `chain_changed`, список перечитывается.
* `profiles_guard` (новая версия в 009): через API роль и выбранное имя меняются только внутри этих функций (метка транзакции `mitzpe.admin_op` + не `anon`/`authenticated`); владелец — только из SQL.
* `admin_list_users(search)` — список для админов: имя, роль, кто назначил и когда. **Без email и без признака «есть ли email».**
* Журнал `role_events` (кто, что, кому, когда; при переименовании — старое и новое имя): пишут только функции; изменения из SQL Editor пишет триггер (`sql_change`, автор — null). Читают админы (`admin_role_log`). При удалении аккаунта id → null, имена в его записях стираются (триггер).
* `campaigns.created_by` ставится автоматически (через API — вошедший админ; в SQL Editor — указанный или владелец), через API не меняется. Старые кампании → владелец.
* Назначение админом (`admin_grant_admin(target, p_confirm_staff)`) и главным админом из ученика (`owner_make_main_admin(target, p_confirm_staff)`) требует `p_confirm_staff = true` — «подтверждаю, что это учитель или сотрудник» (010); без него `staff_not_confirmed`. Подтверждение пишется в `role_events.confirmed_staff`.
* Коды ошибок: `not_logged_in`, `not_allowed`, `bad_target`, `no_username`, `chain_changed`, `unchanged`, `username_taken`, `invalid_username` (detail = код правила имени), `staff_not_confirmed` → `admin.errors.*` / `auth.errors.*` в `strings.js`.

## Редактор лабораторных (шаг 5a)

* **Профиль админа** (`admin_profiles`: `full_name`, `workplace` обязательны, `position` — нет). Пока его нет, все функции лабораторных отвечают `admin_profile_required` (UI показывает ссылку на `/profile#admin-profile`). Новому админу без профиля показывается окно `AdminProfilePrompt` (можно закрыть, при следующей загрузке появится снова). Профиль публичен на лабораторных, которые админ создал или одобрил (показ — 5b); при снятии роли остаётся на них, при удалении аккаунта удаляется (cascade).
* **Статусы:** `campaigns.publication` = `draft` | `in_review` | `published` (старые — `published`) — отдельно от `status` (`collecting` | `completed`, имеет смысл только у опубликованных, меняется в редакторе; при публикации — `collecting`).
* **Черновики:** видны только админам (RLS), в `campaigns` из `useAppData()` только опубликованные, `getObservation()` находит и черновики (у админов); `allCampaigns` — все загруженные. Черновик может быть неполным (пустые названия/подписи, без центра карты) — проверка `campaigns_publishable` только вне черновиков. Поля черновика удаляются по-настоящему (данных нет).
* **Сохранение** — только `lab_save(id | null, edit_no, info, fields)`: всё состояние редактора одной транзакцией (одно `form_version`++). `edit_no` не совпал → `edited_elsewhere` (кто-то сохранил раньше; UI предлагает загрузить заново). Ошибки проверки → `invalid_lab`, detail `{путь: код}`: `info.<колонка>`, `fields.<i>.<свойство>`, `fields.<i>.options.<j>.<свойство>` (i, j — позиция в редакторе). Ключ поля/варианта строится из английской подписи (`fieldKeyFromLabel`), редактируется до сохранения, потом закреплён (как тип и единица).
* **Опубликованные:** через `lab_save` — только косметика: тексты (название, описание, оборудование), подписи, подсказки, порядок полей и вариантов, значок, регион, сложность, центр/зум, пресет цветов, статус. Структура (новые/удалённые поля и варианты, архив, обязательность, min/max/decimals, длина текста, основное поле) и **протокол** → `structural_change` (триггеры, в т. ч. из SQL Editor) — они идут через ревизию (5c, см. ниже). Адрес (`slug`) после публикации закреплён. Подписи опубликованных не могут стать пустыми.
* **Оборудование и протокол** на трёх языках: `equipment_he/en/ru` (старое `equipment` = he, `lab_save` держит его равным `equipment_he` для старого кода), `protocol_he/en/ru` (короткий Markdown, `Markdown.jsx`). Пусто на en/ru → показывается иврит (`labEquipment`, `labProtocol` в `labs.js`); пустой протокол → общие шаги из `strings.js`.
* **Журнал** `lab_events`: `create`, `edit`, `edit_published`, `delete` (+ из 5b: `submit`, `withdraw`, `approve`, `request_changes`, `publish` — автор `null`, «система»; у записей есть `round`); `details` = какие колонки/поля изменились (`lab_snapshot` + `lab_diff`). Название копируется, чтобы запись читалась после удаления лабораторной; имён пользователей нет (только `actor_id`, при удалении аккаунта — null).
* **Точки входа:** «Новая лабораторная» и списки во вкладке «Лабораторные» панели админа; «Редактировать» на странице лабораторной (если `lab_can_edit`); черновик на странице лабораторной — с плашкой «не опубликована», без кнопки добавления измерения.

## Проверка лабораторных (шаг 5b)

* **Раунды:** `campaigns.review_round`. Отправка (`lab_submit`) — новый раунд; сохранение лабораторной «на проверке» (`lab_save`) — тоже новый раунд (одобрения прошлого раунда больше не считаются, из `lab_reviews` ничего не удаляется) и она должна оставаться полной (`not_ready`). У записей `lab_events` есть `round`: правки черновика относятся к следующему раунду (`review_round + 1`), правки на проверке — к новому текущему.
* **Перед отправкой** (`lab_missing` в SQL = `submitChecklist()` в `labs.js`, те же пути/коды): названия и описания на he/en/ru, центр карты, хотя бы одно активное поле, ровно одно активное основное числовое поле, подписи всех полей и вариантов на трёх языках, у полей-выборов хотя бы один активный вариант. Ошибка `not_ready`, detail `{путь: код}`. `checklistItems()` группирует пункты для UI.
* **Кто одобряет** (`lab_review(id, round, 'approve'|'changes', comment)`): любой админ с заполненным профилем, **кроме** автора (`created_by`) и тех, кто создавал/редактировал/отправлял в этом раунде (`lab_round_editors`); один вердикт на админа за раунд. Роль при подсчёте не проверяется — одобрение остаётся в силе после снятия роли. `round` не совпал → `round_changed`. 3-е одобрение → `published`, `published_at`, событие `publish`. «Запросить изменения» — комментарий обязателен (≤2000), лабораторная возвращается в черновик; комментарии видит автор (панель в редакторе) и админы, публично — нет.
* **Отзыв:** `lab_withdraw` — те, кто может редактировать, возвращают «на проверке» в черновик.
* **Очередь:** `lab_review_queue()` — все «на проверке» + `my_state` (`can_review` | `own_lab` | `edited_this_round` | `already_reviewed`). В `useAppData()`: `reviewQueue`, `reviewCount` (сколько могу проверить) — бейдж на вкладке «Лабораторные», у ссылок на профиль в шапке и точка на кнопке меню; `reloadReviewQueue()` после действий.
* **Публичные подписи:** `lab_credits(id)` (все, и без входа): автор и 3 одобривших раунда публикации (полное имя, должность, место работы) + дата; `published_at` пуст (старые) → `{legacy: true}` — «опубликована до взаимной проверки», автор не показывается. Удалённый аккаунт → имя null → «бывший сотрудник». `lab_credits_all()` → строка «имя · место работы» на карточках главной (`credits` из `useAppData()`). Таблица `admin_profiles` публичной не становится.
* **UI:** `SubmitPanel` в редакторе (над вкладками, пункты чек-листа переключают вкладку/язык и подсвечивают недостающие тексты полей; при несохранённых изменениях — «сначала сохраните») и компактно на странице черновика; страница `/labs/:id/review` (сводка `LabSummary` на любом языке, предпросмотр формы, история, «Одобрить» / «Запросить изменения», причина, если нельзя); «Проверить» на странице лабораторной у админов; «Ждут проверки» в начале вкладки «Лабораторные».

## Ревизии опубликованных лабораторных (шаг 5c)

* **Что идёт через ревизию:** новые поля и варианты, архив/возврат поля или варианта, обязательность, min/max/decimals, длина текста, основное поле и **протокол** (он задаёт метод). Косметика опубликованной (тексты, подписи, подсказки, порядок…) по-прежнему сразу через `lab_save`. Удалить поле/вариант опубликованной нельзя — только архив (`must_archive`).
* **`lab_revisions`:** не больше одной открытой (`draft` | `in_review`) на лабораторную; хранит всю предлагаемую форму (`fields` — в формате `lab_save`, в порядке редактора) + `protocol_he/en/ru`. Редактируют те же, кто редактирует лабораторную. `edit_no` у ревизии свой (`edited_elsewhere`).
* **Сохранение** (`lab_revision_save`): проверка как у полей (без обязательных подписей — их требует отправка), `lab_revision_diff` пуст → открытая ревизия закрывается (`discarded`). «Изменилась ли ревизия» — по форме (`lab_revision_shape` = `revisionShape()` в `labs.js`): структура всех полей/вариантов, тексты только новых, без порядка + протокол; правка подписи существующего поля ревизию не меняет (и не сбрасывает одобрения).
* **Проверка:** как в 5b, но свои раунды у ревизии (`lab_revisions.round`), `lab_reviews.revision_id`; не могут одобрять автор лабораторной, автор ревизии (`own_revision`) и редактировавшие ревизию в этом раунде. Отправка — `lab_revision_missing` (подписи на трёх языках, одно основное поле, варианты у выборов). 3-е одобрение → `lab_revision_apply` в той же транзакции (метка `mitzpe.lab_apply`): структура из ревизии, тексты и порядок существующих полей — из живой лабораторной, новые поля/варианты — в конец, протокол; `form_version`++. До этого ученики работают со старой формой (открытая форма после применения получит `invalid_values` → перечитает кампанию).
* **Редактор опубликованной:** состояние = живая + открытая ревизия (`labWithRevision`), у полей/вариантов `inLive`. Одна кнопка «Сохранить» делит изменения (`splitPublished`): косметика → `lab_save` (поверх живой структуры, живой протокол), структура + протокол → `lab_revision_save`. Бейджи «новое / ждёт проверки», `RevisionPanel` (изменения, чек-лист, отправить / вернуть в черновик / отменить, запросы изменений).
* **Очередь и подписи:** в `lab_review_queue` есть `kind` (`lab` | `revision`) и `revision_id`; на странице `/labs/:id/review` у опубликованной с ревизией на проверке — список изменений, «как станет» (`LabSummary` + предпросмотр формы), текущий протокол. `lab_credits` возвращает `update` — последняя применённая ревизия: «Обновлена {дата}, одобрили …» (и у старых лабораторных).

## Округление координат

* `measurements.lat/lng` хранятся округлёнными до 3 знаков (~100 м) для всех лабораторных — точного места нет ни у кого (ни у автора, ни у админов). Сетка, без случайного сдвига.
* База: триггер `measurements_round_location` (миграция 013, `round(x::numeric, 3)`) на insert и изменение lat/lng — обойти из клиента нельзя. Старые строки округляет `013b_round_existing_coordinates.sql` (**разрушающая**, запускать после экспорта CSV и деплоя production). Порядок: 013 (безопасна, совместима со старым кодом) → preview → merge → деплой → CSV → 013b.
* Клиент: `roundCoord`/`roundLatLng` из `src/lib/location.js` (= Postgres `round`) — сразу при выборе на карте и «моём местоположении», точная точка не попадает в состояние мастера. Показ — `locationLabel()` (3 знака); `coordLabel()` (5 знаков) — только для центров карт лабораторных.
* Фото: `stripImageMetadata()` из `src/lib/image.js` перерисовывает файл на canvas (EXIF с GPS пропадает). Не удалось декодировать (например, HEIC в Chrome) → ошибка `wizard.step3.photoUnsupported`, оригинал не прикрепляется.
* Рядом с картой в мастере — `wizard.step1.roundingNote` и `notAtHome`.

## Правила i18n

* Любая новая UI-строка добавляется во все три языка (he, en, ru) в `strings.js`.
* Фоллбэк: текущий язык → иврит → сам ключ (+ предупреждение в dev).
* Названия кампаний, тем и метрик — в данных, поля `titleHe/En/Ru`, `labelHe/En/Ru`. Выводить через `observationTitle()`, `topicTitle()`, `metricLabel()`.

## Правила RTL

* Только логические классы Tailwind: `start-*`, `end-*`, `ms-*`, `me-*`, `ps-*`, `pe-*`. Не использовать `left-*`/`right-*`/`ml-*`/`mr-*`.
* Числа, координаты, единицы — оборачивать в `dir="ltr"`.
* Направление брать из контекста i18n (`dir`, `isRTL`), не хардкодить.

## localStorage

Используется только для `mitzpe.locale` и `mitzpe.theme`, плюс сессия Supabase Auth (`sb-*`, её пишет supabase-js). Данные туда не класть.

* Для изменений больше одного файла — сначала план, код после подтверждения.
* Трогать только файлы, относящиеся к задаче. Не рефакторить попутно.
* Не добавлять TypeScript, новые UI-библиотеки или менять стек без согласования.
* Сохранять дизайн: градиент «небо → песок», frosted glass панели, squircle-иконки. Цвета брать из существующей темы в `tailwind.config.js` (палитра называется «forest»), новые цвета не хардкодить.
* Пользователи — школьники (несовершеннолетние): не добавлять сбор лишних личных данных.
